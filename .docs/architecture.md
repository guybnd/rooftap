## Key Decisions

- **App Router** — Enables React Server Components for data-fetching pages (dashboard, apartment detail).
- **Supabase SSR** — `@supabase/ssr` package handles cookie-based sessions for both client and server components.
- **Scoring at client** — Scoring algorithm runs client-side so it works offline; scores are persisted to Supabase when online.
- **Mobile-first** — All layouts designed for 375px viewport (iPhone SE) first, expanded for tablet/desktop.
- **Realtime sync** — Two layers of Supabase realtime keep collaborators in sync:
  - *Global*, apartment-centric tables stream into `src/lib/data-cache.tsx`, which debounce-refetches the whole dataset on any change.
  - *Section-level*, group-scoped tables use `src/lib/hooks/use-group-table-realtime.ts`. Two entry points: `useGroupTableRealtime({ table, groupId, onChange })` for fine-grained id reconciliation (Groceries, which needs to avoid a cost-line sync ping-pong), and `useGroupTableRefetch({ table, groupId, refetch })` — a debounced wrapper for pages with a single fetch function, which simply re-runs the fetch on any group row change so existing filters (mine-only) + derived data stay correct and the section-cache is refreshed. Adopters: Groceries (`grocery_items` + `grocery_sessions`, FLUX-100, reconcile), Setup (`setup_items`, FLUX-101, refetch), Tasks list + Costs (`household_tasks` + `cost_items`, FLUX-102, refetch). Tables must be in the `supabase_realtime` publication and set `replica identity full` so group-filtered DELETEs are delivered.
  - Multi-writer note: writes are last-write-wins (no version column). For derived writes driven by a reactive effect (e.g. the grocery session→cost-line sync), guard against a realtime echo re-triggering the write on non-originating devices, and protect shared singletons with a DB uniqueness constraint (see the grocery actual cost-line partial unique index).
- **Global capture → documents store** (FLUX-98) — a single **+** entry point (desktop "+ Capture" in `src/components/app-sidebar.tsx`; raised center button over the mobile tab bar via `src/components/capture/capture-buttons.tsx`) opens `src/components/capture/capture-sheet.tsx`. The sheet routes each capture into the central documents store (`src/lib/documents.ts`): **Invoice** → uploads + parses + attaches to a new/existing cost item; **Grocery Bill** → runs the FLUX-95 grocery pipeline unchanged then registers the *same* storage object into the store (no re-upload, hence `documents.source` discriminates the bucket — `signedUrlForDocument` resolves it); **Document/Other** → a details step (FLUX-114) where the user names it (default `category – date[ – OCR title]`, with an amber nudge while the name is still the generic default), picks a `doc_type` category (`SearchablePicker`), and optionally sets an expiry (emphasised for warranty/ID/insurance/vehicle/lease), free-text tags (autocomplete from existing group tags via `listDocumentTags`), a cost-item link, and an opt-in OCR "scan for a title" toggle (parse is intrusive, so off by default). The success toast carries a one-tap **Rename** action (`renameDocument`) as a safety net. The cost-item pickers everywhere use the shared `SearchablePicker` (FLUX-115). **Multi-file** (FLUX-117): "Choose file" accepts multiple — picking >1 routes to a "multi" confirm step (one compact row per file: name, category, expiry, tags, with an "apply category to all" shortcut), batch-uploaded as documents with partial-failure handling and a single success summary; expiry rows auto-create reminders. Open/close state lives in `CaptureProvider` (`capture-context.tsx`), which wraps the shell so the nav buttons (outside `DataCacheProvider`) can trigger the sheet (mounted inside it for the active `groupId`). **Quick-add launcher (FLUX-174):** the "+" now opens a launcher step first — a search field plus a grid of add actions (Cost / Doc·Scan / Grocery / To-do / Checklist / Apartment listing), each shown only when its owning section is enabled (`getEnabledSections()` minus `settings.hiddenSections`, the same check as `app-sidebar.tsx`). Cost / Grocery / To-do open `CostModal` / `GroceryItemModal` / `HouseholdTaskModal` shell-mounted alongside the sheet (writes via the offline-first Legend stores, mirroring `home/page.tsx`); **Doc / Scan** enters the original `source` step so the file/receipt/document capture flow above is unchanged; Apartment / Checklist navigate (`/apartment/new`, `/checklist`). The search field reuses the `/home` global index (`useGlobalSearchIndex` + `useFuzzySearch`) and the "Add '{query}' as… To-do/Grocery/Cost" chips. The launcher opens even offline (offline-first quick-adds still work); only online-only tiles (Doc·Scan, Apartment) disable offline, and the document sub-steps keep their offline gate. Store reads + the documents fetch are gated behind the sheet being open, so shell-mounting adds no always-on sync. The `/documents` browse view (`src/app/documents/page.tsx`, FLUX-105) lists every group document with type/source filters, an in-app preview popup (`document-preview.tsx`, FLUX-122 — images inline, PDFs in an iframe, replaces opening a new tab), full metadata editing (`document-edit-modal.tsx`, FLUX-121/123 — name/category/expiry/tags + cost-link management via `updateDocumentMetadata`/`linkDocument`), delete (storage + row + cascade links), and per-card info chips (FLUX-125 — coloured category, tags, expiry badge, uploader + upload date via `memberProfiles`). Costs cards show a green paperclip when a cost has attachments (FLUX-124). It live-refreshes on `documents`/`document_links` realtime (FLUX-120) and is reached from a cross-section sidebar link and capture toasts. The explorer (FLUX-118) provides multi-select category chips, an expiry-state filter (all/expiring/expired), tag filters (click a card tag to filter), sort (newest/soonest-expiry/name), fuzzy search, and an "Expiring soon" group pinned above the list (≤30 days). Quick presets ("Warranties", "Vehicle", "Insurance", "Leases", "IDs", "Receipts") select a category set in one tap, and documents linked to the same cost render adjacently with a subtle accent (paired-by-cost, FLUX-135). Services read their store-linked documents via `src/components/documents/linked-documents.tsx` (`listDocumentsForEntity`) — wired into the Costs card docs expander alongside the legacy `cost_documents` list.
- **Legacy unification (FLUX-106), read-merge + dual-write — no storage backfill.** Rather than migrating the old file silos, the store *coexists* with them: (1) **read-merge** — `listUnifiedDocuments` unions store `documents` with live legacy rows (`cost_documents` via the cost_items group join, `grocery_sessions.receipt_path`), deduped by storage path (store row wins), so `/documents` shows every file; legacy entries are open-only with a static service chip. (2) **Dual-write** — new Costs uploads also best-effort `registerDocument` + `linkDocument` into the store (failures never break the legacy upload), so going forward they're first-class store rows. (3) **Manage legacy from /documents** (FLUX-138) — a legacy card offers **Adopt** (`adoptLegacyDocument` → registers it into the store + relinks, so it becomes editable) and **Delete** (`deleteLegacyDocument` → removes the object + clears/deletes the origin reference per kind: `cost_documents` row or `grocery_sessions.receipt_path`). `documentBucket(source)` resolves which physical bucket an object lives in (`cost`/`grocery` → `cost-documents`, else `documents`); `deleteDocument` only removes the object when it lives in the `documents` bucket, never a legacy-owned one.
- **Warranties retired → documents (FLUX-132).** The separate Warranties & Receipts section (table `warranty_assets`/`warranty_files`, the `/warranties` page + libs, and the brief `tracked_items` table) was removed. Warranties/insurance/vehicle/lease are now ordinary **documents** — a category + (FLUX-133) `documents.metadata` sub-fields + the explorer's filtered views; expiry reminders and cost links come from the documents model. The Setup page surfaces a setup item's **linked documents** (`document_links` entity_type `setup_item`) in place of the old warranty handoff.
- **Centralized hub / `/home` (FLUX-155).** A cross-section overview page (`src/app/home/`), added as a `home` section in `src/lib/sections.ts` (drives the switcher/tab bar; `getSectionByPath` resolves `/home`; selectable as `defaultSection`; root `/` redirect unchanged). It composes **existing** stores/components — no new Supabase queries or RLS. Files: `page.tsx` (orchestrator — owns the `householdTasks$` store + the `HouseholdTaskModal` and lays out the bento grid), `today-hero.tsx` (converges tasks + reminders + today's appointments into one filterable/checkable/snoozable list; tap = done, swipe right = done, swipe left = snooze 1h/1d/1w, long-press = full task modal, ＋Add = task due today), `groceries-widget.tsx` (compact→expand under 10 needed / navigate at 10+; needed + bought-today + 'have'-lingers-then-fades list; autocomplete quick-add re-flags existing→needed; `SwipeActions` + `GroceryItemModal` reused), `section-tiles.tsx` (budget-aware Costs with `CostModal`, Documents count + capture upload, Setup `SegmentedBar`, Home Search next-appointment + top listing), and `hub-shared.tsx` (the `HubTile`/`AvatarBubble` primitives, hub tunables, the shared `useLongPress` gesture, and `buildHeroItems`). Reuses the one `src/components/ui/swipe-actions.tsx` `SwipeActions` swipe implementation (FLUX-217, generalized out of groceries); `hiddenSections` removes a section's tile, its hero items, and its hero filter tab.
- **Checklists section / `/checklists` (FLUX-156).** A general-purpose group-shared checklist tool, added as a `checklists` section in `src/lib/sections.ts` (nav: All Checklists + Templates; `getSectionByPath` resolves `/checklists` — the legacy singular `/checklist` apartment-scoring route is unrelated and was relabelled "Apartment Checklist"). Four new group-scoped local-first tables (`checklists`, `checklist_task_items`, `checklist_templates`, `checklist_template_items`) via the `createGroupStore` factory (stores in `src/lib/legend/`, registered in `INDEXEDDB_TABLES` with an `INDEXEDDB_VERSION` bump 2→3). Checklists have a **type** (☑ plain / 🔁 repeating / 🛒 shopping) and an optional cross-cutting **date** (`scheduled_date`). All row shapes + cross-section rules live in `src/lib/checklists.ts` (pure builders + completion/recurrence helpers; side-effect-free so every surface agrees). Pages: `page.tsx` (list with type badge + date chip + progress + Start-again), `[id]/page.tsx` (the nexus — item check/attribution/reorder/delete, Shopping cost logging into `cost_items`, the date↔linked-`household_tasks` to-do, checklist↔task completion sync, Repeating cadence/renewal + client-side auto-renew on load, manual Start again), `new/page.tsx` (type picker + date toggle + template picker, seeds starters idempotently), `templates/page.tsx` (user-authored editable templates CRUD). Cross-section integration reuses `householdTasks$`/`costItems$`; the `/home` hub's `buildHeroItems` surfaces a dated checklist's to-do with an "Open →" deep-link + live completion (`checklistByTaskId`), and the Tasks card shows an "Open checklist" backlink for `linked_checklist_id` rows.
- **Recipes section / `/recipes` (FLUX-189).** A group-shared recipe book, added as a `recipes` section in `src/lib/sections.ts` (nav: All Recipes; `getSectionByPath` resolves `/recipes`). Two new group-scoped local-first tables (`recipes`, `recipe_ingredients`) via the `createGroupStore` factory (stores in `src/lib/legend/`, registered in `INDEXEDDB_TABLES` with an `INDEXEDDB_VERSION` bump 3→4). Each recipe has a **method** (cooking/baking/roasting/other, nullable=unset), free-text **cuisine** tags, optional **instructions**, and structured **ingredient rows** (name + optional quantity/unit). All shapes + rules live in `src/lib/recipes.ts` (pure builders + the name-match/have-count/`canBeMade`/unit-step/suggestion helpers; side-effect-free). The recipe↔grocery link is **name-based** (`matchIngredientToGrocery`, reusing the `norm()` `trim().toLowerCase()` precedent) — an ingredient "has it" iff its matched `grocery_items` row is `status==='have'` (presence-based, not quantity-aware). Pages: `page.tsx` (list with fill bar + cuisine/method/"can make now"/search filters + ＋ New recipe), `[id]/page.tsx` (the nexus — live ingredient status, an inline per-ingredient Have↔Need toggle + ＋ Add to list, bulk "Add missing to Need It", edit via the shared form sheet), `new/page.tsx` (deep-linkable create), and `recipe-form-sheet.tsx` (shared create/edit built on the FLUX-182 `ItemFormSheet`; ingredient rows use a Name autocomplete (`ingredient-name-input.tsx` — the one net-new widget), a unit-aware drag-to-adjust Qty (`DragNumberField` + `stepForUnit`), and a bounded Unit dropdown (`SearchablePicker` over `UNITS`)). Cross-section: pushing a missing ingredient writes/patches a `grocery_items` row via the shared `groceryItems$` store (so an open recipe re-renders live on a grocery status change), tagging it with an **ephemeral `recipe_note`** (`"250 g for Lasagna"`) that clears when the item leaves `needed` — never touching the user's own `notes`. A shared `<ProgressBar>` (`src/components/ui/progress-bar.tsx`) was extracted for the fill bar.
- **Recipe ingredient canonical item matching (FLUX-205).** Splits the descriptor from the shopping item: `recipe_ingredients.name` stays the full transcribed/entered line, and a new nullable `item_name` holds the canonical grocery item ("white sugar" descriptor → "sugar" item_name). Every have/need match + grocery-add flow keys on `ingredientMatchKey(ing)` (`item_name ?? name`, `src/lib/recipes.ts`), not `name` alone. `rankItemMatches(query, library)` is a tiered fuzzy ranker (exact norm → singular/plural → token subset → token-overlap) reused by three surfaces: the Gemini recipe-scan pipeline (`src/lib/ai/parser.ts` requires an `item` field per ingredient and is passed the item library in-prompt; `src/lib/recipe-capture.ts` auto-links only the confident exact/plural tiers), the draft-review sheet (`recipe-form-sheet.tsx` renders a silent/unconfirmed-suggestion/new-item state per row, gated on `recipe?.draft`, with a "N to review" banner — Save never blocks on it), and a new per-row **quick-editor sheet** (`ingredient-quick-editor-sheet.tsx`) that edits one ingredient's descriptor/qty/unit/match/Have-Need status in place — opened via long-press → the existing `PopMenu`/`useLongPress` hold-menu on a detail-page row, "Add to list", or a review-sheet "new item" chip — so editing one saved-recipe ingredient never requires the full `RecipeFormSheet`.
- **Fuzzy match candidate library (FLUX-209).** All three `rankItemMatches` call sites above draw their candidate library from `itemMatchLibrary(groceryItems, ingredients)` (`src/lib/recipes.ts`) — the normalized-deduped union of active grocery item names + already-linked canonical `item_name` values, never raw ingredient descriptors. This is deliberately distinct from `ingredientNameSuggestions` (grocery names + raw `ing.name` descriptors), which stays reserved for the ingredient-name **autocomplete** in `recipe-form-sheet.tsx` — a fuzzy match target should only ever be a canonical item name, otherwise a long descriptor line (or a row's own descriptor) can surface as a confusing suggestion chip.
- **Calendar promoted to its own top-level section (FLUX-228).** `/calendar` previously had a standalone page but no owning `Section` — it was nested under Home Search's nav and fell through `getSectionByPath()`'s if-ladder to the `search` section default, so its settings/breadcrumb chrome mislabeled as "Home Search". Now a first-class `calendar` section in `src/lib/sections.ts`, with `CalendarSetup` moved from `globalPanels` to `sectionPanels.calendar`. Also added: a dedicated per-connection "Rooftap" Google Calendar that all pushes target (`getOrCreateRooftapCalendar()` in both `src/lib/google-calendar.ts`/`supabase/functions/_shared/google-calendar.ts`, idempotent get-or-create, new `calendar.calendars` OAuth scope — pre-FLUX-228 pushed events are deliberately left in `primary`, never migrated; `pushEntityForMember`/`removeMemberPush`/`reconcilePush` all try the resolved Rooftap calendar first and fall back to `primary` on a 404), configurable pull window + default import visibility (`google_calendar_connections.pull_window_past_days/_future_days/default_import_visibility`), opt-in undated-to-do timed-block scheduling (`user_settings.calendar_todo_mode/_default_time/_default_duration_minutes` — `all_day` stays the unchanged default), richer pushed-event payloads (`reminders.overrides` from `reminder_lead_days`, appointment `location`, a Rooftap deep-link in `description`), a per-user `timezone` replacing the old hardcoded `Australia/Sydney`, and an independent `calendar_show_pulled_events_in_todo` toggle (surfaced in both `CalendarSetup` and `SectionPreferences`) gating the `/home` hub's pulled-events loop in `buildHeroItems()` separately from the Home Search section-hidden toggle.
- **Calendar settings-driven re-push (FLUX-243).** `reconcilePush` (`supabase/functions/calendar-sync/index.ts`) previously only re-pushed an already-synced mapping when the entity's own `updated_at` outran `mapping.synced_at`, so toggling `user_settings.calendar_todo_mode` to `timed_block` (or any other settings field `buildEventBody` reads — timezone, `reminder_lead_days`, `appointment_duration_minutes`) never retroactively fixed already-pushed events; they stayed all-day in Google until the entity itself was next edited. Now `reconcilePush` also batch-fetches each pushing member's `user_settings.updated_at` (one query for all mappings, not per-mapping) and treats a mapping as stale when that timestamp outruns `mapping.synced_at`, **scoped to entities dated today or later** (`isDatedTodayOrFuture` — task `due_date` / appointment `scheduled_at` >= start of today UTC) so past pushed events are deliberately left untouched by a settings change.
- **MCP server for external agent read access (HOUP-2).** `src/app/api/mcp/route.ts` exposes a stateless `StreamableHTTPServerTransport` (`@modelcontextprotocol/sdk`) so external agents (first consumer: a Telegram bridge, built separately) can **read** household data over `Authorization: Bearer <token>`. Auth is a **Personal Access Token**: `personal_access_tokens` (service-role only, zero client RLS policies — same precedent as `google_calendar_connections`) stores only the SHA-256 hash of each token (`src/lib/pat.ts` — `generateToken`/`hashToken`/`issueToken`/`resolvePatUser`); the raw value is shown once at issuance via `scripts/issue-pat.mjs` and never persisted or logged. A PAT resolves to one `user_id`, then to a `group_id` via `group_members` (`resolveGroupId`), and every tool query is explicitly scoped to that `group_id` through the admin client — the admin client bypasses RLS entirely, so these explicit filters (plus `visibleTasks`/`visibleEvents` replicating the app's `deleted`-tombstone and `private`-visibility JS filters server-side) are the only thing preventing cross-household reads. Three read-only tools ship in v1: `get_budget_summary`, `get_tasks`, `get_upcoming_calendar_events` (native `events` only, not the Google Calendar overlay or `appointments`). No token expiry, no rate limiting — revocation (`revoked_at`, checked live every request) is the only lifecycle control. **This endpoint has no network-level access control of its own and is intended to be reached only over a private network (Tailscale/WireGuard), never exposed via public port-forwarding.**
- **PAT expiry and MCP rate limiting.** A personal access token expires only if its owner picks a lifetime when generating or refreshing it (Never by default, or 30 days, 90 days, 1 year: `PAT_EXPIRY_OPTIONS` in `packages/core/src/pat-expiry.ts`, sent as `{ expiry }` to `POST`/`PUT /api/pat`). `personal_access_tokens.expires_at` is null (or `infinity`, for keys the first 90-day version touched) for keys that never expire; an expired key no longer blocks Generate. Each token is limited to 120 MCP requests per minute through the `pat_rate_limit_hit` Postgres function (per-minute counter rows in `pat_rate_limits`, service-role only), so the limit holds across serverless instances; over budget returns 429 with `Retry-After: 60`. The check fails open on a database error so a counter fault never locks a household out. Both settings panels show the expiry choice and "Expires in Nd", "Never expires" or an Expired state. This supersedes the "no token expiry, no rate limiting" note above; sign-in-based (OAuth) MCP auth is still a follow-up.
- **MCP sign-in (OAuth).** Apps such as Claude connect to `/api/mcp` as a custom connector by signing in to Rooftap instead of pasting a bot API key. `src/lib/mcp-oauth.ts` is a small OAuth 2.1 authorization server: discovery at `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server` (both also answer with a path suffix), open dynamic client registration at `POST /api/oauth/register` (public clients only, redirect URIs must be https or loopback http), the consent page `/oauth/authorize` (signed-out visitors go to `/login?next=…` and come back; the Google path carries `next` in the `rt_login_next` cookie so Supabase's redirect allowlist needs no change), and `POST /api/oauth/token` for the PKCE-S256 code exchange and rotating refresh tokens. Codes live 5 minutes and are single use; access tokens (`rt_oat_…`) live an hour; refresh tokens don't expire but rotate on every use. Everything is stored hashed in service-role-only tables (`oauth_clients`, `oauth_authorization_codes`, `oauth_tokens`, migration `20261020050000_mcp_oauth.sql`). The MCP route tells the two credentials apart by prefix, rate-limits sign-in connections with `oauth_rate_limit_hit` (same 120/min as keys), and answers 401 with `WWW-Authenticate: Bearer resource_metadata=…` so clients can find the flow. A signed-in app gets exactly what a bot key gets: the same MCP settings, modules and household scoping. Both settings panels list connected apps under MCP server with a Disconnect button (`GET`/`DELETE /api/oauth/connections`) and show the connector address. Bot API keys are unchanged.
- **MCP write tools, tasks surface only (HOUP-9).** `create_task`/`update_task`/`complete_task`/`delete_task` join the read tools in the same `route.ts`, deliberately scoped to the tasks surface only — the ticket flagged a one-big-bang write API across every surface (tasks/costs/calendar/groceries) as the wrong shape, and recommended tasks first as the lowest-risk/highest-value surface, with the rest split into their own tickets. Every write re-derives the same explicit `group_id` scoping the read tools use, then re-applies `visibleTasks` (via a new `findVisibleTask` helper: fetch by `id`+`group_id`+`deleted=false`, then the same private-and-not-mine filter) before mutating — an id for another household's task, or another member's private task, resolves to "Task not found" rather than leaking existence or allowing a write. `create_task` mirrors the `/tasks` quick-add defaults (`assigned_to` = caller, `private: false`, `sort_order: 0`, `due_date`/`due_time`/`notes` nullable); `complete_task` stamps/clears `completed_at` the same way the to-do page's checkbox does. `update_task` is a partial patch — only the fields passed are written. Costs/calendar/groceries write tools, and PAT hardening (expiry + rate limiting, since write access raises the blast radius of a leaked token) are tracked as separate follow-up tickets rather than folded in here.
- **MCP write tools, costs surface (HOUP-10).** `create_cost_item`/`update_cost_item`/`delete_cost_item` join the tasks write tools in `route.ts`, using the same `group_id` scoping discipline. Cost items carry no per-user `private` flag (the `cost_items` RLS policy grants every group member full manage access), so the new `findVisibleCostItem` helper is simpler than `findVisibleTask` — just `id`+`group_id`+`deleted=false`, no additional visibility re-filter — but an id for another household's cost line still resolves to "Cost item not found" rather than leaking existence or allowing a write. `create_cost_item` mirrors `src/lib/cost-items.ts`'s `createOneOffCostItem` defaults (`cadence: 'one_off'`, `is_estimate: false`, category `other`) rather than calling that helper directly — it expects an auth'd browser client (`supabase.auth.getUser()`), not the admin client the MCP route uses. It's scoped to one-off cost lines only (name/amount/category/provider/start_date/notes); creating a recurring or `is_estimate` line still requires the Costs page. `update_cost_item` is a partial patch covering the full editable field set from `cost-modal.tsx` (name, amount, category, cadence, `is_estimate`, provider, start/end/discount-end dates, notes) — only the fields passed are written. `delete_cost_item` soft-deletes the same way `delete_task` does.
- **MCP write tools, calendar events surface (HOUP-11).** `create_event`/`update_event`/`delete_event` join the tasks/costs write tools in `route.ts`, native `events` only — same boundary `get_upcoming_calendar_events` already respects (never the Google Calendar overlay `google_calendar_events` or `appointments`).
